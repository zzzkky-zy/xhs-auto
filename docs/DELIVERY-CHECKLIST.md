# 修复固化与交付检查

本清单用于证明修复进入了哪个环节，不代表这些环节已经完成。遵循[升级与回退](UPGRADE-ROLLBACK.md)，不要把一次任务中能用的临时补丁、测试通过或本地提交说成插件已经发布或安装。

## 分开记录六种状态

| 环节 | 必须保存的证据 | 不足以证明完成的情况 |
| --- | --- | --- |
| 问题与修复 | 可复现问题、受影响入口、通用修复、回归用例及仍未解决项 | 仅修改任务脚本、手动修正一次结果、只在交接文字中声称修复 |
| 源码提交 | 仓库地址、分支、完整提交 SHA、工作区是否有未提交变更 | 版本号未变但工作树已变化；只有本地文件或同机 Git bundle |
| 测试验证 | 对应源码 SHA/文件哈希、命令、时间、退出码、执行数、失败数、跳过数与未运行范围 | 静态测试函数数量；旧版本测试报告；部分检查冒充完整验收 |
| 冻结包 | 包版本、构建来源 SHA、构建环境、包 SHA256、逐文件清单、干净解包检查 | 只有压缩包名称；未记录源码来源；包内混入私有状态 |
| 远端发布 | 远端分支实际 SHA、标签指向、发布页及实际资产哈希；仅在用户授权发布时执行 | 本地 commit；推送命令未确认结果；旧 release；只有草稿 |
| 实际安装 | 目标环境、实际加载入口、读取的版本及模块哈希、诊断结果 | 仓库或下载包存在；插件目录搜不到；一个环境通过推断另一个环境也通过 |

“代码已修复”“离线测试通过”“已打包”“已推送”“已发布”“目标环境已安装验证”必须分别表述。源码、文档、skill 和 MCP 入口应来自同一冻结来源；同一个版本字符串不能代替文件哈希比对。

## 每次修复的最小记录

1. 问题：原始错误、发生阶段、是否执行过输入/提交，哪些事实仍未知。
2. 归因：我方可复现缺陷、已证实的平台限制、或原因未明；原因未明不能直接归咎平台。
3. 修改：通用代码、skill/文档、测试分别列出；任务专用恢复措施另列，不混为通用功能。
4. 验证：针对性用例与全量检查分别记录；跳过和未运行不是通过。真实平台未测，应明确注明，不能为验收新增未经授权的外发。
5. 交付：各环节独立标记“完成／未完成／不适用”，写证据；没有证据保持未确认。
6. 遗留：缺失源码、未恢复的后期补丁、未完成的暂停门、状态投影一致性等都必须列入待办，直到对应实现和回归证据齐备后才能关闭。

## 升级不得破坏运营事实

- 升级前停止新领取和外发，保留当前动作、未知结果和所有真实成功回执；不通过重建空库恢复运行。
- 程序和私有状态分离。配置、账号、任务库、动作账本、素材证据与暂停状态不随源码包覆盖；备份沿用最新完整事实，SQLite 使用支持的 backup API。
- 源码回退或旧备份不能抹去后来真实发送、预约或评论的记录。无法确认的结果继续保持未知，不重新提交。
- 原始凭据、会话令牌、私有配置、人物资料和运营账本不进入公共仓库或发布包。脱敏证据副本不能冒充可直接运行的完整状态备份。
- 本地副本、同机备份和 Git bundle 只能说明有本地恢复材料，不能称为异机持久保存。远端保存需使用获准的目标，并回读验证。
- 用户已暂停时，升级、测试通过、验证码消失、服务重启或新的定时唤醒均不构成重新开启授权。恢复只能依据用户明确的后续指令；已有平台预约的处理须遵循该指令，不能随升级擅自改动。

## 发布与安装核对

发布前确认 plugin.json 的 repository 与真实源码仓库相符；版本由维护者按实际发布计划统一修改，不为制造完成感单独递增。检查 VERSION、manifest、包和发布说明一致。

发布或安装不是只读审计的副作用。未获授权时停在可审查的本地变更和验证报告；不要推送、创建 release、替换安装缓存或重启实际运营。获准后逐层核验真实结果，再更新交付状态。
