# Humanizer-zh 怎样参与小红书运营

本包附固定提交 `f4518a8eab97b8bfebc66a89d34320a89bef6930` 的 Humanizer-zh 与 MIT 许可证，来源和文件哈希见 [来源记录](../skills/humanizer-zh/UPSTREAM.json)。它负责编辑已有中文表达，保留信息、确定程度与作者声音；不负责补事实、创作缺失内容，也不保证互动效果或检测结果。

运营从 [主 skill](../skills/xiaohongshu-operations/SKILL.md) 进入，评论读 [原 Soft CTA 全文](../skills/xiaohongshu-operations/references/original-skills/soft-cta/SKILL.md)，帖子读 [原帖子方法与当前接入](../skills/xiaohongshu-operations/references/content.md)。系列图的完整分析、提纲和提示词方法另见[直接读取完整原方法](../skills/xiaohongshu-operations/references/visuals/workflows/README.md)，Humanizer不替代这些创作方法；原帖子与评论 skill 按[内容来源说明](CONTENT-SOURCES.md)直接读取，后加工程记录不改写原内容。开始内容制作前就读取 [Humanizer 原规则](../skills/humanizer-zh/SKILL.md)，起草时应用，草稿形成后仍对这份实际文本做编辑。运行和发送遵循 [RUNTIME](RUNTIME.md)，内容资料怎样注册与绑定见 [内容证据契约](CONTENT-REVIEW.md)。

## 为什么只有读规则和布尔勾选不够

读过规则不等于编辑过这一稿。`humanizer_checked=true` 不说明输入是什么、改了什么、哪份文案通过业务复核、后续是否换过稿。把 draft、final 和固定通过理由一次生成，也不能证明发生了实际前后编辑；事后编差初稿更不算对照。

采用按顺序形成的独立产物：保存来源后创作，保存完整草稿后编辑，保存编辑稿后业务复核，最后固定文案及发布参数。程序检查注册先后、来源和文件哈希、字段一致性、配置与审查版本；这些客观检查仍不能证明 agent 真的读过资料、审过语义或看过图。技术通过和内容验收分别报告。

## 起草前必须带入的材料

| 输入 | 用途与边界 |
| --- | --- |
| 已确认的作者声音样例与来源 | 学用词、语气、判断方式和长短变化，不把样例经历、数字和身份移入新稿 |
| 当前允许事实和核实卖点 | 知道哪些能力、身份、福利能说，哪些需条件或不能说；旧稿不是核实证据 |
| 本条/本帖业务意图 | 知道要回答哪个需求，为什么选 A/B/C 或这个选题，是否需要怎样的引导 |
| 完整来源 | 评论含正文、配图和评论区，帖子含研究来源；引用、作者说法与评论者说法分清 |
| Humanizer 与对外文案规则 | 信息保留优先，同时遵守本项目对外附注文案限制 |

这些材料沿用私有 `content_profile` 的版本与确认来源；缺失项集中向用户确认，不重复询问已确认项，也不替用户写同意。保留态度和自然表达，不能把去空话变成去个性、去立场、去 CTA。原有 CTA 无事实依据时应回业务创作处理，不能由编辑阶段悄悄改任务目的。

## 评论怎样制作

1. 读原帖正文、全部配图、实际评论，判断具体需求、主帖或回复对象和 A/B/C。保存真实快照与可见内容，注册 `source`；没有读到的不补写。
2. 按 Soft CTA 方法创作完整评论，先给有用回应，按已确认A/B/C决定产品表达；B/C保留当前要求的产品定位、适用能力与福利，不在编辑中自行降为纯帮助。应用已读 Humanizer 规则，保存真实 `draft`，包括本条意图和规则路径。
3. 重新读取这份草稿，用前述声音、事实与意图逐句编辑，保存完整 `edited` 与该条实际编辑理由。允许不改，但理由应能对应本条具体表达，不能整批复制已检查保留原稿。
4. 对照来源、配置和两稿，复核需求、事实、身份、建议、语气和 CTA。跨条再看重复开头、统一句式、说教口吻和 A/B/C 策略偏离，不只检查没有违规。
5. 复核通过才注册 `final`，固定全文及目标，原审查绑定此最终 payload。改目标、改文、改配置或来源证据，原审查不再有效。已发稿只供诊断，不能为展示编辑效果补发或替换。

## 帖子怎样制作

1. 来源研究与选题，保存实际材料及研究结论，注册 `source`。
2. 完整创作标题、正文、封面、每页图字、互动和 CTA，保存真实 `draft`。提纲不是完整创作稿。
3. 对实际草稿逐字段编辑，另存 `edited` 及具体理由。补例句、扩写内容、加数据、加能力都属于创作返工，不能记为 Humanizer 去空话的成果。
4. 逐字段业务复核，固定准确文字清单；`pages` 按页号列全部文字，包含页眉、气泡、标签、页脚。无互动可留空并记实际原因；已配置必需CTA时不得留空，实际正文应包含完整意图；其他未要求CTA的账号才可说明无CTA原因。不能用省略号代替待做内容。
5. 按固定清单形成 Naturalizer 方案、准确提示词并制图，逐张打开 PNG 实看，核对图字、额外文字、构图、阅读顺序、主体和品牌。Humanizer 管文字，Naturalizer 管视觉，不能互相代替。
6. 图片文字需变更则回文字流程，重新编辑和复核；只修渲染问题则修图后重新实看。最终标题、正文、图序与设置核对后注册 `final`，附逐页图字和实际观察，再进入原审查和授权。

## 编辑时的判断，不是一套替代质量的指标

保留信息、数字、先后顺序、条件、否定、归因和作者立场，不强化效果。用词变自然不能把可能写成确定、计划写成完成、参考回答写成一定拿 offer。原帖、来源链接、任务号、原数据、代码、配置和已发记录保持原样。

空泛、重复或拗口才改；有用的口头表达、态度、必要重复和真实犹豫可以留。不要统一改成冷静中性的小教程，也不要把每条开头变成你说什么、可以先做什么。长度、改字比例、关键词命中或自评分不能代替语义核对。

每条简短编辑理由说明实际发生的事。例如指出删掉哪处重复、保留哪项条件、某个开发者句为何有必要。若没有改动，可以说明哪项细节使回应具体、哪项事实与条件已核对；这不是可批量粘贴的通过句。不要输出思维链。

## 对外成品与内部资料分开

全部小红书对外字段服从 [文案规则](../skills/xiaohongshu-operations/references/audience-copy.md)：不加声明、解释或免责附注。生成来源、材料性质、未核实事项及审查理由留内部；不为删除附注补造作者亲历。内容句自身必要的真实条件仍需准确表达，不能删去条件后靠附注兜底。

真实草稿、编辑稿、编辑理由、逐字段业务复核、逐页文字和验图观察保存在原批次私有 `output_dir`，不进 Git 或安装包。只把同一份固定最终稿和实际验看的 PNG 写入获准 payload；发送未知仍先查原任务，不能新编号重发。过程证据保存到什么阶段就报告到什么阶段，不用记录存在冒充语义合格。

## 历史对照的证据边界

[当前规则](RUNTIME.md) 保留当时文件，作为已有稿件编辑的历史示例；不证明本轮逐阶段制作、全部字段复核、Soft CTA 业务恢复或质量验收。旧稿里的附注和表达不作为当前新稿模板。当前验收必须使用同批真实来源，展示本轮真正形成的阶段稿与逐页图字，不能用教学样例或历史已发稿替代。

插件同时携带运营与 Humanizer 两个 skill，通过完整包安装。此流程由宿主 agent 执行，不是执行器临发送自动改稿服务，也不增加任何发送或长期日程授权。

本轮简化只减少普通发送的记录搬运：固定稿仍经真实阶段与业务审查，发送MCP内部核对和归账；不会让执行器临时改文，也不要求agent再手动建立同内容任务、调用发送、调用归账三次。具体接口以运行契约为准。
