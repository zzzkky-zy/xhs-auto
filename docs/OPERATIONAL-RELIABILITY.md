# 自动化运营可靠性：机制与验收路线

更新：2026-10-22。本文是通用工程设计和验收路线，不是已实现、已发布或实机通过的证明。代码改进和离线测试不授权真实账号操作；业务暂停状态保持不变，恢复必须遵循实际用户指令。

## 1. 结论与证据分层

目标不是“永不出现平台故障”，而是让故障不导致重复发送、记录失真、全局停摆或反复打扰用户；可恢复问题尽量由有界流程自行处理，不可恢复问题一次性准确交接。

证据标记：
- **V：当前可验证。** 当前仓库、原规则与代码可直接检查。设计审计基线为 c809a03；本轮实现状态及最终测试数量应由最终验证报告更新，不由本文预先宣布。
- **H：历史记录待恢复。** 历史事故与处理记录存在，但原截图、数据库或修复文件尚未完成当前版本的证据核验。可用来设计回归场景，不能据此宣称修复已在当前版本。
- **D：拟议机制。** 尚需实现与验收；不能算作已完成。

已直接阅读：docs/RUNTIME.md、docs/CLOUD-BROWSER-RECOVERY.md、docs/CLOUD-HOST-ACTIONS.md、skills/xiaohongshu-operations/SKILL.md，以及cloud_actions/cloud_batch相关接口。历史事故用于提出故障假设；每项实施前应核对原始证据和当前代码。版本与发布状态需要独立核实，不能把其他版本的测试数量套用到本版。

## 2. 系统结构：一个事实源，五个可解释控制面

1. **事实账本**：追加保存动作意图、许可、真实执行、回执与证据；任务列表、批次摘要、日统计全部是投影，不各自创造事实。
2. **计划编译器**：把平台约束、明确用户配置、业务skill默认值编译成版本化计划；冲突必须明确显示，不靠执行时临场猜测。
3. **权限与风险边界**：动作语义、账号、目标、内容类别、许可出处分开表示；本地配置不能伪造外部工具授权。
4. **执行与恢复状态机**：单账号串行、有界恢复、页面所有权、读取与写入分离；未知不是失败，失败也不全是平台问题。
5. **交付链**：修改→回归→提交→包→远端发布→安装指纹→实机能力验证，逐层证明，不能跳级宣称完成。

## 3. 事故—机制—验收矩阵

### P0-01 持久状态和环境交接（V+H）
- 事故：换环境后原任务目录/修复材料缺失；本地代码包含未远端覆盖的修改。历史发送记录不完整，容易把“未读到”误当“没执行”。
- 根因：临时执行盘、源码交付和业务状态备份被混为一种持久化；摘要没有强制可验证的材料清单。
- 曾有效：保存原编号，冻结素材，数据库备份API，校验hash；同字节材料迁移时保留来源。不重建空库重跑。
- 反模式：只备份聊天摘要、拷贝运行中SQLite文件、把本机副本称异机备份、旧备份覆盖新发送事实。
- D：版本化交接manifest含账号/state_id、各库checkpoint、事件高水位、未决动作、素材hash、代码commit、配置指纹；开机先读manifest并检查引用。缺库时只读恢复，不初始化空库。安全备份与可分享脱敏报告分离，禁止token进交付包。
- 回归：在提交前/提交后回执落盘前/投影更新前逐点故障注入；旧快照恢复必须识别缺口，禁止重发；迁移缺一个文件时返回具体缺项。
- 指标：已确认回执恢复丢失数=0；无证据自动重发=0；交接完整性检查覆盖率100%；记录恢复耗时，不先承诺固定秒数。

### P0-02 事实源与陈旧投影（V+H）
- 事故：某个评论主动作记录为not_applied、无输入无Send，任务镜像仍submitted_unknown；CURRENT-RUN说明也曾陈旧。
- 根因：多个状态表独立更新且没有投影版本/新鲜度；用户可见状态把镜像当权威。
- 曾有效：核对原动作和原回执；原绑定reconcile刷新投影，不改历史。
- 反模式：看镜像重发、直接改SQLite状态、用摘要覆盖更晚回执。
- D：读状态同时返回authoritative_status、projection_status、source_event_id、projection_lag；显式幂等rebuild projection只读取账本生成镜像，不改变动作结果。摘要显示“镜像待同步”，不能误报未知发送。
- 回归：主账本与镜像不一致、重启中断、重复同步、乱序事件；结果不可从unknown变success除非有独立真实证据。
- 指标：不可解释状态冲突=0；投影滞后可观测率100%；相同事件重建结果一致。

### P0-03 未知结果、未执行和重试（V+H）
- 事故：工具在输入前拒绝与提交后响应丢失曾共用含混失败描述；旧retry逻辑容许形成链，可能不断重新尝试。
- 根因：网络/工具返回与实际副作用边界没有被统一表达。
- 曾有效：记录零输入零Send证据，明确not_applied；Send前落盘，单次提交；未知保留现场。
- 反模式：超时即失败；用新operation_id绕去重；不明确结果重发；无限retry链。
- D：区分not_started、input_denied、prepared、submit_started、submitted_unknown、confirmed；一次root最多一个独立重试child，只有确认未执行且新增相关授权/修复证据才允许；成功和未知禁止重试。提交token消费与日志事务必须先于外部动作。
- 回归：重复点击、重复工具响应、并发创建重试、重启后重试、子重试再试、同内容新ID、外部拒绝但本地仍继续；都不能产生第二次未授权Send。
- 指标：每许可Send次数≤1；重复发布/评论=0；未知动作保存率100%。

### P0-04 用户暂停是真正停止，不是只停新领取（V+H）
- 事故：用户暂停后旧执行进程/已领取动作仍可能持有写许可。当前文档明确queue暂停只影响新领取。
- 根因：调度开关与执行撤销语义混在一起。
- 曾有效：关闭外部自动任务，保持已有平台预约不变，明确等用户再开启。
- 反模式：验证码消失自动恢复；旧唤醒重新启动；暂停被下一批配置覆盖；把暂停当撤销已预约帖子。
- D：分别保留queue_pause和用户execution_stop；后者有持久generation，每个新副作用前校验。已在外部提交中的动作允许回执落盘但不再追加动作；恢复需明确用户指令且重新核身份/额度。
- 回归：claim后暂停、输入后暂停、Send已开始后暂停、跨进程旧generation、定时唤醒、扫码完成；必须仅允许必要只读与归账。
- 指标：停止生效后新副作用=0；暂停后自动恢复=0。

### P0-05 自然日额度与跨日排期（V+H）
- 事故：前日不足额的评论不应补算到前日；预约跨日帖子已占次日配额，不能由新批次重置。
- 根因：批次计数、实际发生时间、预约发布日期和账号自然日被混淆。
- 曾有效：账号时区日汇总、实际成功与未知分别统计、保留原预约；跨日按实际发布日计配额。
- 反模式：每批重置日额度、按UTC统计、只数主评、不计回复、跨日租约完全忽略、临时挤压间隔追赶配额。
- D：账号级日账本绑定IANA时区；评论主评+回复共享额度；已成功+已保留名额+可信未归账上界保守核算。计划表按实际日历/平台档位编译，历史例外明确scope，不扩散到新批。
- 回归：23:59到00:00、主评/回复混合、并发批次、未知提交、夏令时通用账号、旧批例外、新批剩余额度不足；不回填过去。
- 指标：超额/错日归账=0；预约间隔违规=0；已预约内容重复占额=0。

### P0-06 授权证据与外部拒绝（V+H）
- 事故：公开产品邀请被误解成实际私信；已有许可反复索要，降低执行效率。
- 根因：操作语义与内容语义没有结构化；代理自述不能替代真实用户授权；外部工具许可与本地闸门混用。
- 曾有效：读取原用户问题和答复、精确账号、公开受众与承诺边界；公开邀请、实际私信和权益发放是不同动作。
- 反模式：堆更多“已授权”布尔值；把本地修复当解除外部拒绝；自动换工具绕过；泛化一次授权到全部营销。
- D：许可引用保存验证来源和适用范围，区分public_comment、private_message、benefit_fulfilment；同范围已有许可复用，不反复问；工具拒绝保留原因与是否执行，新相关证据仅支持有界重试，仍拒绝就停此动作。
- 回归：公开邀请vs实际DM、授权撤回、内容承诺变化、其他账号、证据来自第三方、同证据重复重试。
- 指标：无变化重复授权询问趋近0；许可越界=0；外部拒绝绕过=0。

### P0-07 挑战/故障与恢复证据（V+H）
- 事故：安全验证、二维码身份确认、renderer error9、控制会话故障不同；reset曾易被表述成浏览器重启。
- 根因：缺乏层次化故障分类与能力探测；把时间流逝或tab消失当恢复。
- 曾有效：原页面+通道诊断、单次官方支持恢复、需账号持有人完成的App扫码交接、新鲜精确身份与挑战消失后才解锁。
- 反模式：循环换URL/浏览器、通过新会话躲限制、kill进程清cookie、猜平台限流原因、过期handoff冒充当前页。
- D：结构化incident包含action ownership、控制健康、页面状态、challenge/rate/permission各独立枚举unknown/yes/no、允许恢复能力；恢复permit一次消费。handoff绑定实际tab并有可核时戳，用户返回只触发验证不直接恢复写入。
- 回归：tab消失但challenge latch仍在、身份错号、只reset解释器、二维码过期、恢复返回丢失、已授权普通CAPTCHA但要求手机身份验证。
- 指标：无证据解锁=0；同incident恢复次数有界；平台归因必须有证据。

### P1-08 历史缺口不能一刀切停止所有独立任务（H，适用规则需复核）
- 事故：旧评论记录不全曾导致今日全停，原skill只要求有记录时做作者去重。
- 根因：把“无法证明全部历史”扩成新前置条件，超过原规则。
- 曾有效：保留已知作者/未知目标排除，建立当前自然日可信基线与剩余额度，只继续可独立验证目标。
- 反模式：空库推断今天0；忽略未知风险；反过来因一个旧只读unknown挡住全部新阅读。
- D：风险作用域细化为account/write/target/author/read；缺历史输出uncertainty budget及具体禁用对象。若当日剩余额度无法可信估算仍停写，但来源研究等无副作用工作可继续。
- 回归：只缺三日前历史、缺当日成功上界、一个目标unknown、纯读取未知、已知作者重复。
- 指标：安全可执行任务被无关阻塞占用的时间；不以降低安全标准追求完成量。

### P1-09 页面所有权与资源回收（V+H）
- 事故：多标签积累、renderer崩溃；页面复用偏离原规则；无法精确归属的同URL页面不能随意关。
- 根因：动作生命周期没有强制绑定owned tab及可清理证据。
- 曾有效：每逻辑动作新页、成功/确定未发送后关闭自己的页；未知保留；有界原生内存诊断而非OOM猜测。
- 反模式：为提速复用未经许可的旧页；按URL猜归属；关用户页；以任务管理器可见部分内存冒充总内存。
- D：owned resource registry绑定operation/tab/context；终态自动产生cleanup候选，执行前核对所有权与现场，成功close读回inventory；unknown保留并设置数量/资源阈值，触发停止新增而非删证据。
- 回归：同URL两页、close响应丢失、tab ID重用、终态前清理、崩溃但未提交、用户页混入。
- 指标：健康已终态owned tab遗留数量；峰值资源与崩溃频率；错误关闭=0。

### P1-10 共享预算、缓存与有效阅读（V+H）
- 事故：重复展开全部评论、反复读规则和整池导致慢；搜索/阅读计费粒度容易漏算卡片。
- 根因：把内容新鲜度和完整重读混为一谈；不同执行进程各自预算。
- 曾有效：完整读过证据同批复用，发送前只刷新真实目标、作者、当前评论与账号；每卡独立扣共享读取预算；页面动作与高层预算分开。
- 反模式：缓存命中伪称新读；为fresh绕预算；评论数未变就断言无新内容；1–5秒页面操作误改搜索/读帖限制。
- D：统一account budget service及明确charge unit；证据缓存含已读范围、read_at、内容指纹和失效条件；freshness policy按动作风险分层，不机械重读所有楼中楼。调度取各适用期限最大值，只抽一次持久化，不层层追加等待。
- 回归：多执行进程交替读写、缓存命中、新卡弹层、嵌套评论未展开、等待期间重启、到期继续不重抽。
- 指标：有效阅读/总阅读比、重复读占比、预算违规=0、非必要固定等待时长。

### P1-11 内容阶段和图像质量（V+H）
- 事故：来源不足、阶段勾选冒充完成、真人封面只比hash、不完整示例或泛化模板易造成低价值内容。
- 根因：流水线只验“存在文件”，未验真实阶段依赖、教学价值及视觉差异。
- 曾有效：满足配置数量的合格来源完整正文+图片证据，source→draft→edited→final实际产物，逐图实看，历史真实封面对照，素材固定hash。
- 反模式：旧池冒充当期新研究；只换衣服文字不看图；生成图未验就提交；将用户截图改动当真实性证据。
- D：阶段DAG和invalidate rules；同字节迁移不使审查全失效，内容/素材改变则使后续相关审查失效。质量门包括完整示例+可复制模板、事实出处、CTA精确匹配、真人数量与视觉对比记录；保留人工/模型实看边界，不将hash称视觉验收。
- 回归：换内容不重审、图片内容改变但文件名同、同图不同压缩hash、引用来源未读完、缺固定CTA、伪造经历、题目相邻重复。
- 指标：返工率、来源复用率（透明）、完整示例覆盖率100%、视觉检查覆盖率100%。

### P1-12 发布配置回读与请求/结果分离（V+H）
- 事故：群、活动、模板标签、原创声明和实际预约时间可能与请求不同；活动自动加话题容易被误删。
- 根因：把点击成功当选中结果，正文与平台派生元数据混写。
- 曾有效：实际选中回读、原正文/CTA保持、模板话题和活动话题分开、后台回执核对、不重提已成功发布。
- 反模式：群缺失换其他群；自动删活动话题；报告“公开发布”但只预约；旧租约过期不敢读取回执。
- D：publication manifest分别保存requested/observed；硬性用户指定对象不可自动替换，可选fallback由配置明确；回执读取是独立只读权限，不延长写租约。完成状态拆prepared/scheduled/public_visible，不自动跨级。
- 回归：对象不可选、活动额外话题、原声明默认勾选、半小时档位、预约成功响应丢失、写租约过期后读取真实结果。
- 指标：已选对象回读覆盖率100%；请求与实际差异未报告=0；重复预约=0。

### P1-13 配置优先级与规则漂移（V）
- 事故：通用运行文档的默认间隔及页面操作期限可能与账号当前确认的配置不同；skill模板缺失fallback不一定适用于用户硬性指定对象。
- 根因：通用默认、用户特定配置、平台强制条件、历史例外散落文档。
- D：配置编译时展示effective_rules及来源，优先顺序为强制限制/权限边界→最新明确用户要求→已确认业务配置→skill默认。无法同时满足则报具体冲突，不能静默取宽松值。例外附生效批次/截止/账号，不能继承到新批。
- 回归：后改规则只作用新批、旧预约不变、模板fallback禁止、比例C不足时A/B合规分配、配置更新后老grant仍引用旧指纹。
- 指标：运行时临场重新解释规则次数；同配置计划可重复生成一致结果。

### P1-14 版本交付与真实性（V+H）
- 事故：修复在任务里测试过，却没有全部进入当前仓库、远端或安装版本。
- 根因：完成定义只到“本次能继续”，没有发布闭环；修复和任务恢复脚本混放。
- D：每条事故有issue/test/commit/release/install证据链；通用runtime、skill、schema、文档同步修改。临时恢复脚本只能带单次用途标签，不冒充公共API。构建manifest含源码commit、dirty标记、工具链、测试报告hash、包hash；安装端报告实际fingerprint。
- 回归：dirty工作区打包、源码与schema不同步、版本相同代码不同、远端未包含commit、旧安装未更新；拒绝“已全部发布”状态。
- 指标：未远端保存的修复数量、提交到安装滞后、实际安装指纹一致率；完整交付定义不以测试项数量代替覆盖。

### P2-15 调度、通知与运营成效
- 事故：逐步播报、同阻塞反复追问、夜间通知；配额压力导致无价值评论风险。
- D：调度把依赖阻塞与独立可做项目分开，阻塞指纹去重；夜间非紧急延迟并合并，真实需要决定才通知；用户明确暂停后不再主动催扫码。内容价值优先，允许诚实不足额，不用低质内容凑数。
- 回归：重复定时任务遇同challenge、无新信息、夜间、用户暂停、成功数未达目标；只通知一次必要变化。
- 指标：每成功动作工具调用数、人工介入次数/有效完成量、重复通知数=0；另观察有效互动质量，不以条数单独衡量。

## 4. 推进顺序与退出标准

1. **第一阶段：先可信。** 恢复/核对代码和数据谱系；P0事实源、禁止重试链、停止闸门、额度、权限/挑战边界。每项必须有故障注入负例；不能只测happy path。
2. **第二阶段：再高效。** P1缓存/阅读粒度、资源生命周期、配置编译、内容DAG、发布回读。先测当前基线耗时，再比较p50/p95与非必要调用；不缩安全期限来制造提速。
3. **第三阶段：可持续交付。** 每项登记实现/测试/打包/部署/实机五态；有源码与离线通过但未实机验证时明确标候选。没有实际执行授权时不得拿真实账号试发；暂停期间保持只读和离线验证。
4. **复盘常态化。** 新事故先分类：插件bug、配置冲突、宿主能力限制、平台明确响应、未知。只把可泛化的修复合并到插件；账号、文案、授权、token、素材路径留在包外。
