# 首批验收、持续运营与资源清理

本说明按2026-10-15用户最新要求维护：安装和基础配置一次，完整首批由用户验收内容质量；通过后agent在用户和agent约定的业务范围内研究、制作、自审、预约发布和评论，不逐条请求人工审核。每日目标、批次量、关键词、热门池门槛、执行时段随任务调整，记录最新约定即可，不写死旧数量，也不因正常换选题、改稿或换图片要求重新验收。账号、业务目的或权限范围改变仍须有相应真实授权。

## 一次配置与验收

首次配置先完整执行[逐步引导](first-time-setup.md)，默认当前设备和自动保存位置；不要求用户先提供表达样例，先做1篇图文和5条评论本地样稿，再按实际反馈保存口吻。默认质量标准沿用当前完整方法；长期运行与通知不作为首次问卷。

真人封面先询问是否允许，保存 `cover_person_enabled` 及 `confirmation_sources.cover_person_enabled`。拒绝则无需照片、不阻塞配置，也不使用真人封面。允许才请用户上传模特照片（不限定本人），按 [gbro-cover-design](visuals/modules/gbro-cover-design/guide.md)实看清晰正脸、无遮挡、非AI生成，并记录用户上传或指定来源。允许但未收到图可以暂存其他配置，真人资料标记待补，不能宣布完整配置完成；内页仍无真人；用户已明确每批至少一篇真人封面时，记录 content_requirements.min_person_covers=1 并执行，不重复询问。

原图长期保存在包外私有素材目录，不能放源码、安装缓存或会随结案清理的 `operation-runs`；目录与文件沿用私有资料权限。现有 `content_profile` 增加 `face_reference={file,sha256,source_ref}`，`file` 是真实私有绝对路径，`sha256` 是该文件实际的 64 位 SHA256，`source_ref` 和 `confirmation_sources.face_reference` 指向用户上传或明确指定的记录。读取当前完整配置后合并新增字段，再正常 `configure` 保存：程序不会逐字段合并 `content_profile`，不能只传人脸字段覆盖原人设、卖点等资料。沿用账号、授权、任务和回执；原 skill 的 `assets/my-face.png` / `config.md` 在此连接到已有包外私有配置，不另建一套偏好库。

已有业务配置未记录真人选择时先询问；拒绝则不使用真人封面，允许但没有人脸图时，第一次选择真人封面前请用户补图并按上面正常保存，不重建账号或任务库。每次真人封面前，agent核对文件存在可读、哈希匹配、用户来源，并实看参考图；不能把当前程序返回“配置已保存”当作已验证人脸。新配置中允许真人但缺少有效文件、哈希或来源时程序返回待补项；是否真实人脸、照片质量及使用授权仍由agent实看并依据用户提供的材料判断。旧配置缺少选择字段不自动推定允许。

制作真人封面时，把原图准确字节复制到本批 `work/sources/`，作为该帖 `source.sources` 的额外 `snapshot` 注册，真实爆款来源仍单独满足原研究要求。现有来源记录会绑定及复核参考图字节，生成工具必须实际接收这张图作图1。缺图、哈希不符、来源未确认或工具不能接收参考图时，该真人封面待完成，不以文字描述、随机人物或 AI 生成人脸代替；其他已具备材料的工作沿原任务继续。

默认当前设备，自动验证宿主有唯一浏览器、可靠持久磁盘、图像生成/查看、模型调用、按时唤醒和人工接管入口。执行主机不确定就只准备，不凭本机检查宣称云端已接入。skill和MCP本身不运行模型，也不能在退出后自行叫醒agent；在用户指定的云端宿主建立长期任务，不能用本机定时任务代替云端。通知只报告需要人处理、实质失败或用户要求的结果；状态不变时安静。

使用MCP工具`manage_operation_run(operation, data)`，或同主机CLI：

```sh
python3 runtime/xhs_ops.py --config <私有配置> operation-run <操作> --data <私有JSON文件>
```

1. `configure`：首次保存`authorization_ref`（实际用户持续运营授权位置）、`quality_standard`（完整内容质量标准）、`allowed_tools`及私有`content_profile`，字段与确认来源见[内容审查契约](../../../docs/CONTENT-REVIEW.md)。缺少用户确认的资料可以暂存，不能冒充已确认配置用于发送。后续仅修订内容配置时保留原授权、账号、任务及回执，旧审查随配置版本变化失效。首批仍为`validation_required`，不能把历史单篇测试当作完整首批通过。
2. `begin`：传`plan_ref`及`plan`对象，保存本轮和用户约定的实际目标、批量、题材、时段等；评论计划另存A/B/C整数名额`comment_strategy`，按已确认策略和fallback分配，不自行改成全A。返回`id`、目录和阶段；已有未结束批次返回同一编号，换agent继续它。任务调整可用update传入run_id、新plan和plan_ref；这更新后续计划，不篡改已发送内容。要停止尚未执行的旧任务，用cancel传run_id和task_id；只允许取消queued，正在发送或结果未知的动作先核对。每份素材和计划只写入该目录的`work/`或`final/`。
3. 按实际形成顺序完成来源、初稿、Humanizer编辑及最终业务复核，每阶段单独用`update(run_id, content_record={id,stage,artifact})`注册本批目录内的完整文件，stage依次为source/draft/edited/final。具体字段、逐页图字及审查要求见内容审查契约；不得事后补造较差初稿或用摘要替代实际稿件。原`item={id,stage,next_step,...}`仍可记录小型进度摘要，不能替代内容阶段证据。局部失败只返工相关阶段，已成功和未知任务均保留。
4. `schedule`：传`run_id`、`count`及有时区的`first_at`，取得持久的`schedule_slots`。首次时间应为提交完成预留余量，符合平台1小时至14天的预约窗口。相邻发布时间随机60–90分钟；重启、换agent或重调直接沿用。每个发布任务独占一个位置；已有提交保留，其余未绑定位置可用replace_unsubmitted=true和新的count/first_at重排。仍queued的旧任务须先明确取消，running/unknown/blocked的位置不能释放。返回new_slots是这次新安排的位置；这是显式改计划，不是重启重抽，仍须内部审查。跨批也检查已有预约，不能排到已保留帖子的一小时内。
5. `review`：传`run_id`、`payloads=[{tool,payload,content_id},...]`及实际跨条审查`evidence`，绑定已注册的真实阶段文件、配置版本、计划和最终参数。旧`checks`布尔值不能作为准入证据。agent仍须实际审读事实、需求、作者声音、业务引导与图片；程序只核对完整性、哈希及配额，不代替语义判断。稿件或图片变化后重新编辑和复核，自动模式不找用户逐条批准。预约发布时间必须来自该批已保存的slots。视频使用独立画面文字、字幕、真实素材哈希和实际观看记录，按内容审查契约注册，不套用图文pages或省略视频实看。
6. 普通发送直接用原MCP工具，可带 `run_id`、`approval_ref`，一次完成已审稿核对、执行和归账；省略批次时唯一匹配已审目标、文字与素材。跨时间或后台批量才用 `submit_task(...,run_id=<本批编号>)`。首批沿本次真实实跑授权，后续已验收的自动批次不再逐条人工批准。执行器固定排队图片副本并核对内容指纹，已有间隔、账号核对和未知结果保护共用，不因路径不同重复发送。
7. 本批每条任务确定结束后`finish(run_id)`，outcomes分别汇总成功、失败和取消，允许部分成功结案；前置任务明确失败时，未执行的依赖任务跳过，独立任务继续。running/unknown/blocked仍须保留处理。首批为`awaiting_acceptance`并保留素材，用户实际确认完整首批内容质量后才调用`accept(run_id,human_acceptance_ref)`。每类启用的评论/发帖流程都须真实成功，读取测试不能代替。accept不创建宿主日程或打开技术写开关。

首批一旦验收，后续每批由agent自审，最多按原流程返工3轮；仍不合格则放弃该稿并记录，在原定总量内另换题或未发送目标补齐，同时推进其他合格内容；不降低质量、不擅自减量，也不把正常返工交回用户。未知或可能已发送的任务先核对，不另编号补发。每次唤醒先读取status中的continuous_operation、pending_tasks与同一批记录，不重新安装、重新登录或从头研究。

## 动态热门池

热门池是本批搜索和筛选的结果，会随时间改变，不是永久固定的帖子清单。携带run_id的新批搜索会首次实际刷新；同批相同查询可短期复用，继续遵守搜索预算。研究时按笔记编号去重，并如实记录来源、read_at和指标；只有需要最新内容的目标再刷新。不能把上批旧结果称为本批新搜结果，也不为“每次应该不同”强行丢弃仍然合格的重合帖子。

默认不下载别人的配图，网页只保留本次需要的页面。临时热门池和大响应随已确认完成的批次清理；防重复评论、作者去重和发布所需的小记录独立保留，不受临时池清理影响。若任务要求保留跨批研究结论，只保存小摘要和原观察时间，不保留整页截图或图片。

## 低配主机与清理

一个账号只运行一个网页动作；本地整理、写稿和审查可利用排队时间进行。每批只保持当前素材在内存，图像按文件传递，不把整批PNG转为base64放进上下文。每个网页缓存最多32项且8MiB，单项超过2MiB不缓存；三类缓存合计上限24MiB，这不包括浏览器和模型本身。完成批次经MCP finish/accept/maintain关闭服务自有空闲页并清空缓存；不碰用户标签页或可能含未知发送证据的页面。

清理只管理`output_dir/operation-runs/<run_id>/`且所有权标记匹配的目录，不扫描删除用户旧材料、浏览器profile或其他文件。已确认完成且不再需要人工验收的批次立即删除工作图、最终图及固定副本；写任务压成小记录，保留任务号、指纹、状态和批准引用，供防重发与查账。原Go提交账本保留，不能以清理为由重建空账本。

明确放弃且无待执行/未知任务的批次默认保留72小时，再清掉；可在私有配置`retention.abandoned_keep_hours`调整。活跃、待人工验收、blocked或unknown批次保留，不按时间盲删。后台每小时及批次结束时检查一次，不访问平台。清理后SQLite空闲页会供后续复用，不保证文件立即缩成零。

临时批次目录默认预算256MiB（`retention.managed_disk_limit_mb`可调），达到预算不再开新批或复制素材，先清理已完成资料；仍超出则保存进度并报告资源问题。0.4.1另检查状态目录512MiB预算、两个分区至少2GiB空闲和1024个可用文件编号；已入队任务资源不足不扣尝试次数，恢复后自动继续。独立读取大响应默认24小时清理、独立写任务大参数/响应7天后缩小，待验收和未知证据仍保留，小型发送与去重记录长期保留。暂停队列也每小时维护；缓存及空闲自有页由程序回收。

这些是程序检查，不是操作系统磁盘配额；外部制图生成前也须检查余量。Debian宿主按[云端资源配置](../../../docs/CLOUD-RESOURCES.md)设置后台与专用浏览器合计约3GiB硬预算，保留其他长期任务空间。只使用远程模型和逐张制图，不在云端安装本地模型。全部本批素材放在带所有权标记的目录，不能每次检查另存完整报告或不断积累旧安装包；只留一份滚动状态、当前与一份回退程序。不要为了节约空间删除未知证据或登录profile。宿主硬限制及实际长期占用仍需云端实测。

## 先修复、再把修复留给下一次

用户已授权agent在当前业务范围内维护本运营skill。普通选择器变化、页面结构变化、等待条件、网络短暂故障、单项质量问题先由agent定位；同一根因最多尝试2种有证据的修复，不循环重启或一直重试。

评论若停在open_input，先查持久记录与具体日志步骤，确认是否为not_applied。当前网页动作使用独立新页、原鼠标点击占位框、逐字输入和单次提交；外围不再插入页面冻结、输入租约、展开专用几何分支或阶段估时取消。只针对实际失败步骤做最小修复，不用聚焦或直接插入文字代替正常展开。只有明确未发送才恢复原任务；unknown先保留证据，不能靠改代码再点一次。失败页面未经核对不清理，本地复现也不能直接当作真实平台根因。

有效技术修复按下面顺序保留：

1. 保存根因、当前任务号、失败阶段与最小证据，查询同一提交记录；未知发送先核对，不能靠修代码再点一次。
2. 在唯一源码中修改最小相关代码和skill说明，以冻结提交作为候选；补能复现实际故障的小验证，或用明确不会发送的检查验证。不编辑安装缓存。内容规则修订必须保留已验收质量标准及事实边界，不能为了让检查通过降低标准、扩大权限或加速频率。
3. 检查后更新运营skill入口/相关参考或执行程序，记录新版本、改动、验证和恢复位置，再切换执行版本，沿原任务继续。原Humanizer文件及许可证不改。软件更新不得覆盖包外账号配置、验收记录和任务账本。
4. 冻结实际新版本后运行scripts/verify_engineering.py，生成检查报告；`repair`除failure、change、verification、before_version、after_version、rollback_ref、skill_update外，还须给verification_report的绝对路径。它核对冻结状态、新版本、实际本地工具检查，以及当前程序和全部运行模块哈希；只填“已修复”不能通过。此工具不代替实际改文件与切版本。记录最多20条，恢复副本仅留当前可用版本及一份必要回退版本，不堆积旧压缩包。当前源码、私有资料与实际加载位置从项目README和运行契约读取，不沿用旧工作副本。
5. 新版检查失败退回上一可用版；两种修复均失败且缺少后续修复授权，或遇确需用户处理的权限、资源及结果核对问题时才请求人工处理。用户已明确允许继续同范围有证据的修复时沿该授权推进，不重复索取同一许可；仍不能推断unknown未发送或扩大外发数量。

登录过期、验证码、账号错配、权限/费用需用户决定、平台明确限制、状态损坏、发送结果无法确认，属于需要正常人工介入的情况。自动运营不包含自动扫码、发送验证码、换号/换设备或改变业务授权。300013不作为调快频率的实验目标；不按定时探针反复撞墙。普通运行无须用户审核每篇，用户随时可暂停、撤回授权或调整任务。
